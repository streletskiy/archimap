# Release Versioning

## Source of Truth

- Release version is derived from Git tags in the `X.Y.Z` format.
- Build metadata includes:
  - short commit hash
  - build UTC timestamp
  - dirty flag (when working tree has changes)

Generated files:

- `src/lib/version.generated.json` (backend)
- `frontend/src/lib/version.generated.json` (frontend)

Both files are generated by [`node --import tsx scripts/generate-version.ts`](../../scripts/generate-version.ts) and should not be committed.

## Release Flow (Tag-based)

1. Ensure the target commit is on `master` and CI is green.
2. Create and push tag:
   - `git tag 1.4.2`
   - `git push origin 1.4.2`
3. [`.github/workflows/docker-release.yml`](../../.github/workflows/docker-release.yml)
   builds `linux/amd64` and `linux/arm64`, then publishes both
   `streletskiy/archimap:1.4.2` and `streletskiy/archimap:latest`.
4. Create the GitHub release only after the Docker workflow succeeds.
5. Verify:
   - `GET /api/version` returns `version: "1.4.2"`
   - `/info` shows `1.4.2 (<commit>, <buildTime>)`
   - both Docker tags contain `linux/amd64` and `linux/arm64`

## Local Verification

1. Run `npm run build`.
2. Run `npm run version:print`.
3. Confirm generated JSON contains expected `version`, `git.commit`, and `buildTime`.

## Build Without `.git`

- If Git metadata is not available (for example Docker build context without `.git`), generation does not fail.
- Version falls back to `package.json` version and includes `buildTime`.
- The script logs a warning:
  - `[version] git metadata is unavailable, using package.json fallback`

## Docker Release

Pushes to `dev` automatically publish the single-platform development image
`streletskiy/archimap:dev` through
[`.github/workflows/docker-dev.yml`](../../.github/workflows/docker-dev.yml). This
workflow targets `linux/amd64`.

Pushing an `X.Y.Z` tag automatically publishes the multi-architecture release image through
[`.github/workflows/docker-release.yml`](../../.github/workflows/docker-release.yml). The
workflow publishes the immutable version tag and moves `latest` to the same image only after a
successful build. It also verifies that both tags contain `linux/amd64` and `linux/arm64`.

The local scripts remain available as a manual fallback or for publishing to another registry.

Build and push image via registry:

Scripts:

- [`scripts/release-docker.ps1`](../../scripts/release-docker.ps1)
- [`scripts/release-docker.sh`](../../scripts/release-docker.sh)

- `./scripts/release-docker.ps1 -Version 1.2.3 -Latest`

Deploy on server via layer-based pull:

- `docker pull streletskiy/archimap:1.2.3`
- `docker compose up -d`

Do not use tar-based transport (`docker save` / `docker load`) for releases, because it forces full image transfer and bypasses efficient layer reuse.
